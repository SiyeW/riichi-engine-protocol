# Riichi Engine Protocol

The engine declares the data it can provide through an output contract. An engine can provide multiple outputs at the same time, and the host can assign different outputs to different engine configurations. The engine's model structure, training methods, and internal data structures are not part of the protocol.

The engine process communicates with the host using JSON-RPC 2.0 and JSONL. This document defines the engine package, process communication, game input, output declarations, weight requirements, initialization, analysis requests, and standard output data. Game data is only applicable to four-player Riichi Mahjong.

## Protocol version

The protocol identifier is fixed as:

```json
{
  "name": "riichi-engine-protocol",
  "major": 2,
  "minor": 1
}
```

Parties with different `major` must not continue communication. In the `engine.hello` request, the host provides the highest `minor` it supports; the engine returns the highest `minor` that both sides support, which must not exceed the value requested by the host. Increasing `minor` can only add negligible fields, methods, or capabilities and must not change the meaning of existing fields and methods.

Output contracts have independent versions. Having the same protocol version does not mean that both parties support the same outputs; the host only uses outputs it recognizes and that the engine has declared. The engine declaring additional outputs must not cause the host to reject the entire engine.

## Process and transport

The host directly launches the engine executable, without concatenating commands through the Shell. The engine reads messages from standard input, writes messages to standard output, and writes logs to standard error. Standard input and standard output use UTF-8; each line must contain exactly one complete JSON object, ending with `\n`. Protocol lines must not exceed 8 MiB, and empty lines can be ignored.

All messages comply with JSON-RPC 2.0:

| Message | Required Fields | Description |
| --- | --- | --- |
| Request | `jsonrpc`, `id`, `method`, `params` | `jsonrpc` is fixed as `"2.0"`; `id` is a non-empty string or integer generated by the host. |
| Successful Response | `jsonrpc`, `id`, `result` | `id` must match the request. |
| Error Response | `jsonrpc`, `id`, `error` | The structure of `error` is described in the 'Error' section. |
| Notification | `jsonrpc`, `method`, `params` | Does not include `id`, the recipient must not reply. |

The host sends requests and notifications to the engine; the engine only sends responses and notifications to the host and does not call host methods in return. A request must receive exactly one successful response or an error response. JSON numbers must be finite, and boolean values are not considered numbers.

When a parsing error or invalid request prevents the recipient from obtaining the request ID, the error response uses `null` with `id`. Apart from this, the response ID must match the request exactly.

## Engine package

The engine package uses `engine.json` as the entry point. The package can be located in a read-only directory; weight files and user settings are not part of the engine package and are not written back to that directory.

```json
{
  "schemaVersion": 2,
  "id": "example.engine",
  "name": "Example Engine",
  "version": "1.0.0",
  "sourceUrl": "https://github.com/example/example-engine",
  "protocol": {
    "name": "riichi-engine-protocol",
    "major": 2,
    "minor": 1
  },
  "entrypoints": {
    "windows-x64": {
      "executable": "runtime/example-engine.exe",
      "arguments": []
    }
  },
  "licenses": [
    {
      "name": "Apache License 2.0",
      "path": "LICENSE"
    }
  ],
  "notices": [
    {
      "name": "Third-party notices",
      "path": "THIRD_PARTY_NOTICES.md"
    }
  ]
}
```

| Field | Required | Format and Meaning |
| --- | --- | --- |
| `schemaVersion` | Yes | Fixed as `2`. |
| `id` | Yes | Stable engine ID using lowercase ASCII letters, digits, periods, and hyphens; length `3..128`. |
| `name` | Yes | Default user-facing name; length `1..128`. |
| `version` | Yes | Engine version using Semantic Versioning. |
| `sourceUrl` | No | The public source code address corresponding to the current package. |
| `protocol` | Yes | the protocol name and highest version implemented by the engine. |
| `entrypoints` | Yes | Nonempty platform entry object. Platform keys use lowercase ASCII letters, digits, and hyphens. |
| `entrypoints.*.executable` | Yes | the executable file path relative to `engine.json`. |
| `entrypoints.*.arguments` | Yes | an array of string parameters; each item is passed as an individual argument. |
| `licenses` | Yes | a non-empty array of license files. |
| `licenses[].name` | Yes | the name of the license. |
| `licenses[].path` | Yes | the license file path relative to `engine.json`. |
| `notices` | No | Array of additional documents such as third-party statements, with fields identical to `licenses`. |

Paths within the package must uniformly use `/`, must not be absolute paths, must not contain empty segments, `.`, or `..`, and after resolution must still be within the package directory. The host only selects the entry that fully matches the current platform and sets the package directory as the process working directory.

`engine.json` does not declare engine type, output, weight format, parameters, or runtime capabilities. After the host starts the process, `engine.hello` must be used as the sole basis for this information and verify that the engine ID and version returned in the handshake match the package.

## Common data types

### Output reference

Output references are used in handshakes, initialization, and analysis requests:

```json
{
  "id": "opponent-shanten",
  "version": 1
}
```

| Field | Required | Format and Meaning |
| --- | --- | --- |
| `id` | Yes | the stable ID of the output contract. Use lowercase ASCII letters, numbers, and hyphens, with a length of `3..128`. |
| `version` | Yes | Output contract major version; an integer of at least `1`. |

When changing the meaning of a field, probability conditions, target definitions, or deleting existing fields, `version` must be increased. Adding optional fields that the receiver can ignore does not require increasing the major version.

### Multilingual text

The engine provides titles and descriptions for users to read using multilingual text objects:

```json
{
  "default": "Backbone weights",
  "en": "Backbone weights",
  "zh-CN": "主模型权重",
  "ja": "基盤モデルの重み"
}
```

| Key | Required | Format and Meaning |
| --- | --- | --- |
| `default` | Yes | the text used when no matching language is found, with a length of `1..256`. |
| Other Key | No | BCP 47 language tag and its text, length is `1..256`. |

The host tries the complete language tag, the primary language tag, and `default` in order. All text is displayed as plain text, without interpreting HTML, Markdown, or terminal control characters.

### Probabilities and discrete distributions

The probability must be a finite JSON number within the closed interval `[0, 1]`, and cannot be `NaN` or infinity. The sum of the probabilities in the probability distribution must be `1` within a `1e-4` tolerance.

Discrete distributions use the following structure:

```json
[
  {"value": 1000, "probability": 0.10},
  {"value": 2000, "probability": 0.25},
  {"value": 3900, "probability": 0.45},
  {"value": 8000, "probability": 0.20}
]
```

`value` must be a string or a finite JSON number, and it must not be duplicated within the same distribution. The order of the array has no protocol significance; the host may rearrange it according to the output contract and display requirements. Each item's `probability` represents the probability of the corresponding value, and values that are allowed but not listed are considered to have a probability of `0`. The specific output contract may further restrict the type and value range of `value`.

### Numeric predictions

Tile counts, dora counts, and scores use the same numeric prediction container:

```json
{
  "distribution": [
    {"value": 1000, "probability": 0.10},
    {"value": 2000, "probability": 0.25},
    {"value": 3900, "probability": 0.45},
    {"value": 8000, "probability": 0.20}
  ],
  "expectedValue": 3955
}
```

A numeric prediction supports two representations:

| Symbol | Corresponding Field | Format and Meaning |
| --- | --- | --- |
| `distribution` | `distribution` | Discrete probability distribution. |
| `expected-value` | `expectedValue` | The mathematical expectation of the predicted value must be a finite JSON number. |

In numerical prediction, `distribution`'s `value` must be a finite JSON number. String values are only for use by other output contracts that adopt a discrete distribution and cannot be used to compute `expectedValue`.

The current engine configuration determines which representations are used for each output during initialization. Declared fields must appear in every corresponding result afterward, and undeclared fields must not appear. If both representations are declared, `expectedValue` must equal the weighted average of `distribution` within the absolute or relative tolerance of `1e-4`.

Count distributions must use nonnegative integers; score distributions must use nonnegative integer points. Their `expectedValue` must not be less than `0` and need not be one of the discrete values that can actually occur.

### Tiles

Physical tiles use the following strings:

```text
1m..9m, 1p..9p, 1s..9s, 5mr, 5pr, 5sr, E, S, W, N, P, F, C
```

`5mr`, `5pr`, `5sr` represent red fives. `?` represents a concealed tile that is not visible in the current input mode and can only appear in game events, and cannot appear in candidate actions or output results.

The prediction output by tile type uses 34 types of tiles, without distinguishing red fives. The key name is:

```text
1m..9m, 1p..9p, 1s..9s, E, S, W, N, P, F, C
```

A complete result must contain exactly these 34 keys. Physical tiles in action data may retain red-five markers.

### Seats

Seats use absolute numbers `0..3` and do not rotate with the current dealer or interface perspective. For opponent predictions from a controlled seat, `players` must contain exactly the other three distinct seats and must not contain the controlled seat.

### Game events

`analysis.run.events` uses MJAI event objects arranged in the order they occur. Each request carries the full history of the current round, with the first item required to be `start_kyoku`, and optionally, an item `start_game` can be included before it. The engine may cache common prefixes but must not require the host to send only incremental suffixes.

Each event has a string field `type`. The protocol defines the following events:

| `type` | Required Field | Meaning |
| --- | --- | --- |
| `start_game` | None | A game begins. |
| `start_kyoku` | `bakaze`, `kyoku`, `honba`, `kyotaku`, `oya`, `dora_marker`, `scores`, `tehais` | A hand begins; `scores` contains the four players' scores, and `tehais` contains four starting-hand arrays. |
| `tsumo` | `actor`, `pai` | The specified seat draws a tile. |
| `dahai` | `actor`, `pai`, `tsumogiri` | The specified seat discards a tile; `tsumogiri` is a Boolean. |
| `chi` | `actor`, `target`, `pai`, `consumed` | Chi; `consumed` contains exactly the two physical tiles used from the hand. |
| `pon` | `actor`, `target`, `pai`, `consumed` | Pon; `consumed` contains exactly the two physical tiles used from the hand. |
| `daiminkan` | `actor`, `target`, `pai`, `consumed` | Daiminkan; `consumed` contains exactly the three physical tiles used from the hand. |
| `ankan` | `actor`, `consumed` | Ankan; `consumed` contains exactly four physical tiles. |
| `kakan` | `actor`, `pai`, `consumed` | Kakan; `pai` is the added tile, and `consumed` contains the three physical tiles from the original pon. |
| `reach` | `actor` | Announce Riichi for the corresponding seat. |
| `reach_accepted` | `actor` | Riichi is accepted and the riichi stick is paid. |
| `dora` | `dora_marker` | A new dora indicator is revealed. |
| `hora` | `actor`, `target`, `pai` | Winning hand; when self-drawing, `target` equals `actor`. |
| `ryukyoku` | None | Draw. |
| `end_kyoku` | None | The current round has ended. |
| `end_game` | None | The current game has ended. |

`actor`, `target`, and `oya` use absolute positions. `bakaze`, `dora_marker`, `pai`, `consumed`, and `tehais` use strings defined in the 'tile' section. `kyoku` is an integer, `1..4`, `honba`, and `kyotaku` are non-negative integers, and `scores` contains exactly four integers. Events can include settlement, display, or source fields; the recipient must ignore known additional fields they do not use themselves, but must not continue reasoning after unknown `type`.

Entering `standard`, the controlled seat's starting hand uses actual tiles, while other seats' starting hands use an equivalent amount of `?` as placeholders; other seats' unrevealed draws also use `?`. Tiles that have been revealed through discards, calls, dora indicators, or settlements use actual tiles. `revealed` input also records the concealed tiles and draws in the score record as actual tiles.

### Candidate actions

The candidate actions of `action-recommendation` are validated by the host according to the rules. Each action contains `type` and `actor`, where `actor` must be equal to the requested `controlledSeat`.

| `type` | Other Required Fields | Meaning |
| --- | --- | --- |
| `dahai` | `pai`, `tsumogiri` | Discard one physical tile. |
| `reach` | None | Declare riichi. |
| `chi` | `target`, `pai`, `consumed` | Chi. |
| `pon` | `target`, `pai`, `consumed` | Pon. |
| `daiminkan` | `target`, `pai`, `consumed` | Daiminkan. |
| `ankan` | `consumed` | Ankan. |
| `kakan` | `pai`, `consumed` | Kakan. |
| `hora` | `target`, `pai` | Win by discard or self-draw; when self-drawing `target` equals `actor`. |
| `ryukyoku` | None | Declares allowance for a draw that players can actively choose. |
| `none` | None | Give up the current optional action. |

Tile fields and arrays in actions follow the rules of the corresponding game events. A `none` action may include a stable `variant` describing the skipped action. When an ankan may be declined after riichi, use `variant: "skip-ankan"` and also provide the forced tsumogiri tile as `pai` with `tsumogiri: true`.

The host must retain every physically distinct candidate, including tsumogiri and hand discard of the same tile and different red-five combinations. `candidateId` is used only for correlation within one request. The engine must not interpret its string structure or merge candidates on its own based on action content.

## Standard output contracts

| Output contract ID | Meaning |
| --- | --- |
| `action-recommendation` | Recommend a candidate from the legal action candidates provided by the host, and can provide evaluation metrics for each candidate. |
| `opponent-shanten` | Predict each opponent's shanten distribution and, conditional on tenpai, the probability of furiten or no yaku. |
| `opponent-deal-in-probability` | Predict the deal-in probability when controlled seats play the 34 tile types to each opponent. |
| `opponent-concealed-tile-count` | Predict the number of the 34 tile types in each opponent's concealed tiles. |
| `opponent-dora-count` | Provide a dora-count prediction for each opponent. |
| `opponent-score` | Provides score predictions for each opponent. |
| `wall-tile-count` | Predict the number of the 34 tile types that have not yet been revealed and are still in the wall. |
| `kyoku-outcome` | Predict the probability that the current kyoku ends in a draw and each player's win, deal-in, and conditional target probabilities. |
| `kyoku-score-delta` | Predict each player's score change from the current position through settlement of the current kyoku. |
| `match-placement` | Predict each player's final placement when the current match ends. |
| `match-score` | Predict each player's final point-stick score when the current match ends. |

`opponent-dora-count` and `opponent-score` each specify the recommended statistical interpretation. The protocol does not require the engine to adopt this interpretation, nor does it set additional declaration fields for other interpretations. The host parses the results according to the output structure, numerical range, and the representation determined at initialization.

## Handshake and output capabilities

After the host starts the process, it first calls `engine.hello`:

```json
{
  "jsonrpc": "2.0",
  "id": "host-1",
  "method": "engine.hello",
  "params": {
    "protocol": {
      "name": "riichi-engine-protocol",
      "major": 2,
      "minor": 1
    },
    "host": {
      "id": "example.host",
      "version": "1.0.0"
    }
  }
}
```

`params.protocol` is the highest protocol version supported by the host. `params.host.id` is the host stable ID, with the same format as the engine ID; `params.host.version` uses Semantic Versioning. Repeated calls to `engine.hello` within the same process must yield the same identity, capability upper limits, weight slots, and parameter schema.

Successful result:

```json
{
  "protocol": {
    "name": "riichi-engine-protocol",
    "major": 2,
    "minor": 1
  },
  "engine": {
    "id": "example.opponent-engine",
    "name": "Example Opponent Engine",
    "version": "1.0.0"
  },
  "outputContracts": [
    {
      "id": "opponent-shanten",
      "version": 1
    },
    {
      "id": "opponent-deal-in-probability",
      "version": 1
    }
  ],
  "weightSlots": [],
  "devices": [
    {
      "type": "cpu",
      "title": {"default": "CPU"}
    }
  ],
  "runtimeCapabilities": {
    "multipleSessions": true,
    "concurrentRequests": false,
    "cancellation": true
  },
  "optionsSchema": {
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "type": "object",
    "properties": {},
    "additionalProperties": false
  }
}
```

| Field | Required | Format and Meaning |
| --- | --- | --- |
| `protocol` | Yes | the negotiated negotiated protocol version. |
| `engine.id` | must be completely consistent with `engine.json.id`. |
| `engine.name` | Yes | the user-facing engine name. |
| `engine.version` | must be completely consistent with `engine.json.version`. |
| `outputContracts` | Yes | a non-empty output declaration array that may be provided by the engine, and must not be duplicated. |
| `weightSlots` | Yes | an array of weight slots; use an empty array if no weights are needed. |
| `devices` | Yes | Nonempty device array listing the device types accepted by initialization requests. |
| `devices[].type` | Yes | a stable device ID, using lowercase ASCII letters, numbers, and hyphens. |
| `devices[].title` | Yes | a multilingual device name. |
| `runtimeCapabilities` | Yes | process execution capability. |
| `optionsSchema` | Yes | a JSON Schema Draft 2020-12 object schema; when there are no parameters, the empty object schema from the example is used. |

Each output declaration includes:

| Field | Required | Format and Meaning |
| --- | --- | --- |
| `id` | Yes | the output contract ID. |
| `version` | Yes | the main version of the output contract. |
| `representations` | Conditionally required | Representation that can be used for numerical prediction, allowed values are `distribution`, `expected-value`. |
| `supportsRevealedHands` | No | Whether to accept revealed-hand input, default is `false`. |
| `metrics` | Conditionally required | `action-recommendation` Evaluation indicators that can be provided; use an empty array if there are no indicators. |

`representations` is only used for outputs that allow numeric prediction representations and must be a non-empty array with no duplicates. Other outputs must not provide this field. `metrics` is only used for `action-recommendation`.

`engine.hello` returns the capability limits of the engine program. The initialization result must return the actual capability based on the current weights and valid parameters, and must not add outputs, representations, evaluation metrics, or explicit support that were not declared in the handshake.

All three fields of `runtimeCapabilities` are required boolean values:

| Field | Meaning |
| --- | --- |
| `multipleSessions` | Whether one initialized instance can isolate multiple `sessionId` values. When `false`, the host uses one session at a time. |
| `concurrentRequests` | Whether multiple analysis requests may run concurrently. When `false`, the host sends them serially. |
| `cancellation` | Whether the engine handles `request.cancel` notifications. |

The host must not infer runtime capabilities from the output contract. The host can retain the original parameters even if it does not recognize the interface extensions in `optionsSchema`, but it must not bypass the standard JSON Schema validation.

## Standard and revealed input

The analysis request uses two input modes:

| `inputMode` | Transmit Content |
| --- | --- |
| `standard` | Information normally available to the controlled seat, including its own concealed hand; other players' concealed hands remain unknown. |
| `revealed` | The complete hand information actually recorded in the game record. It can only be used when the game record indeed contains this information. |

All outputs must accept `standard`. `supportsRevealedHands: true` indicates that the output also accepts `revealed`.

When the interface has not enabled revealed hands, the host always uses `standard`. When the interface has enabled revealed hands, only outputs that meet the following conditions simultaneously use `revealed`:

- The initialization result declares that this output supports revealed hands;
- The current game record contains complete concealed-hand information.

If either condition is not met, the host still passes `standard` data to that output. Different outputs from the same engine may support revealed hands differently. Outputs requiring different input modes must not be combined in the same `analysis.run` request.

## Weight slots

The engine declares weight files that need user configuration in `engine.hello` through `weightSlots`. An engine can declare multiple slots or may not require any weights. Each slot receives one file; when multiple files are needed, multiple slots are declared.

```json
{
  "weightSlots": [
    {
      "id": "backbone",
      "title": {
        "default": "Backbone weights",
        "zh-CN": "主模型权重"
      },
      "description": {
        "default": "Shared feature extractor used by the selected outputs.",
        "zh-CN": "所选输出共用的特征提取权重。"
      },
      "formats": [
        {
          "id": "example-backbone-onnx",
          "extensions": [".onnx"]
        }
      ],
      "requiredForOutputs": [
        {"id": "action-recommendation", "version": 1},
        {"id": "opponent-dora-count", "version": 1}
      ]
    }
  ]
}
```

| Field | Required | Format and Meaning |
| --- | --- | --- |
| `id` | Yes | the internal stable slot ID of the engine. Use lowercase ASCII letters, numbers, and hyphens, with a length of `1..64`. |
| `title` | Yes | a multilingual slot title. |
| `description` | No | Description of multilingual slots. |
| `formats` | Yes | a non-empty array that lists the weight format accepted by the slot. |
| `formats[].id` | Yes | the engine-defined stable format ID. |
| `formats[].extensions` | Yes | Non-null extension arrays, such as `.onnx`, `.pth`. Only for file selection prompts. |
| `requiredForOutputs` | Yes | A non-empty output reference array. This slot must be provided when any of its outputs are enabled. |

A single output can require multiple slots, and a single slot can be shared by multiple outputs. The host determines which slots need to select files based on the outputs currently configured for the engine; slots that are not needed can be displayed in a dimmed manner. The file extension cannot replace the engine's verification of the file's content and structure.

## Initialization

`engine.initialize` loads the current configuration. After the process starts, it must not choose default weights on its own; `analysis.run` must not be accepted before successful initialization. Re-initialization will first terminate the current task, clear all sessions, and then replace the old configuration with the new one.

### Initialization request

```json
{
  "enabledOutputs": [
    {"id": "action-recommendation", "version": 1},
    {"id": "opponent-dora-count", "version": 1}
  ],
  "weights": [
    {
      "slotId": "backbone",
      "format": "example-backbone-onnx",
      "path": "C:\\Models\\Example\\backbone.onnx"
    }
  ],
  "device": {
    "type": "cpu"
  },
  "options": {}
}
```

| Field | Required | Format and Meaning |
| --- | --- | --- |
| `enabledOutputs` | Yes | the non-empty output reference array that must be provided for this load, and must not be duplicated. |
| `weights` | Yes | the weight slot for the currently enabled output requirements. An empty array is used when there are no required slots. |
| `weights[].slotId` | Yes | A currently required slot from `engine.hello.weightSlots[].id`. |
| `weights[].format` | Yes | the format ID of the current slot declaration. |
| `weights[].path` | Yes | Local absolute path resolved by the host. |
| `device` | Yes | device selection; `device.type` must come from `engine.hello.devices`. |
| `options` | Yes | a parameter object validated according to the option structure declared by the engine. |

Each request must provide a file for every currently required slot and must not include unknown, duplicate, or currently unnecessary slots. The engine must validate the file format and content, and cannot rely solely on the file extension.

The file summary is calculated by the host when it needs to identify the source of the results, and it does not require the engine to verify or echo it through the initialization request.

### Initialization result

```json
{
  "outputs": [
    {
      "id": "action-recommendation",
      "version": 1,
      "metrics": [
        {
          "id": "q-value",
          "title": {"default": "Q value"},
          "format": "number",
          "fractionDigits": 3,
          "preferredDirection": "higher"
        },
        {
          "id": "policy",
          "title": {"default": "Policy"},
          "format": "percentage",
          "fractionDigits": 2,
          "preferredDirection": "higher"
        },
        {
          "id": "expected-placement",
          "title": {"default": "Expected placement"},
          "format": "number",
          "preferredDirection": "lower"
        }
      ],
      "primaryMetricId": "q-value",
      "recommendationMetricId": "policy"
    },
    {
      "id": "opponent-dora-count",
      "version": 1,
      "representations": ["distribution", "expected-value"],
      "supportsRevealedHands": true
    }
  ],
  "device": {
    "type": "cpu"
  },
  "effectiveOptions": {}
}
```

`outputs` must contain exactly one result with the same ID and version for every requested output. Array order has no protocol significance. Initialization may narrow the representations, evaluation metrics, or revealed-hand support declared during the handshake, but must not add capabilities. If any requested output cannot be provided, initialization fails as a whole; the engine must not silently remove it.

For numerical predictions, `representations` in the initialization results is a fixed representation that must be used every time a result is returned after the current configuration. For action recommendations, the rules for `metrics`, `primaryMetricId`, and `recommendationMetricId` are detailed in the 'Evaluation metric declarations.' The host arranges the interface according to these fixed statements; the interface structure must not be changed if a single result lacks data.

`device` is the device actually used by the engine and must come from the handshake declaration. `effectiveOptions` must pass through `optionsSchema` in the handshake and include the final parameters after applying default values from the application. After modifying enabled outputs, weight files, devices, or parameters, reinitialization is required.

```json
  "id": "host-41",
  "method": "analysis.run",

    "controlledSeat": 0,
    "inputMode": "standard",
    "events": [
      {
        "type": "start_kyoku",
        "bakaze": "E",
        "kyoku": 1,
        "honba": 0,
        "kyotaku": 0,
        "oya": 0,
        "dora_marker": "3p",
        "scores": [25000, 25000, 25000, 25000],
        "tehais": [
          ["1m", "2m", "3m", "4p", "5p", "6p", "7s", "8s", "9s", "E", "E", "P", "P"],
          ["?", "?", "?", "?", "?", "?", "?", "?", "?", "?", "?", "?", "?"],
          ["?", "?", "?", "?", "?", "?", "?", "?", "?", "?", "?", "?", "?"],
          ["?", "?", "?", "?", "?", "?", "?", "?", "?", "?", "?", "?", "?"]
        ]
      }
    ],
    "outputs": [
      {
        "id": "action-recommendation",
        "version": 1,
        "parameters": {
          "candidates": [
            {
              "candidateId": "candidate:0",
              "action": {
                "type": "dahai",
                "actor": 0,
                "pai": "1m",
                "tsumogiri": false
              }
            }
          ]
        }
      },
      {
        "id": "opponent-dora-count",
        "version": 1,
        "parameters": {}
      }
    ]
  }
}
```

| Field | Required | Format and Meaning |
| --- | --- | --- |
| `sessionId` | Yes | State-isolation key. Different games, controlled seats, and input modes must not share one. |
| `controlledSeat` | Yes | a controlled absolute seat, integer `0..3`. |
| `inputMode` | Yes | `standard`, or `revealed` when supported by the negotiated capabilities. |
| `events` | Yes | the array of standard events that conform to the input pattern up to the current position. |
| `outputs` | Yes | the non-empty output array for this request, which must not contain duplicates. |
| `outputs[].id` | Yes | the initialized output contract ID. |
| `outputs[].version` | Yes | the initialized main version of the output contract. |
| `outputs[].parameters` | Yes | Parameters defined by the output contract; use `{}` when it defines none. |

All outputs in the same request use the same history, controlled seats, and input patterns. Only outputs delivered to the same initialized engine configuration can be merged. The engine must return all outputs in the request and must not add extra outputs; if any output fails, the entire JSON-RPC request returns an error and does not return partial results.

Subsequent requests of the same `sessionId` can extend, revert, or rewrite history. The engine can internally reuse unchanged common prefixes, but it must adhere to the complete `events` this time and discard any state that no longer matches after a rollback or branch. Whether and how to reuse history is up to the engine implementation and does not need to be declared to the host. The host uses the request ID and its own execution generation to determine whether the result is still applicable to the current position; outdated results must not overwrite current data.

## `opponent-dora-count`

```json
{
  "players": [
    {
      "seat": 1,
      "prediction": {
        "distribution": [
          {"value": 0, "probability": 0.20},
          {"value": 1, "probability": 0.40},
          {"value": 2, "probability": 0.25},
          {"value": 3, "probability": 0.10},
          {"value": 4, "probability": 0.05}
        ],
        "expectedValue": 1.4
      }
    }
  ]
}
```

The recommended statistical interpretation is the total number of dora counted when the corresponding player wins the current hand, conditional on that player eventually winning. Ron and tsumo are not distinguished. The count includes regular dora and red fives; after a riichi win, it also includes ura-dora revealed at settlement. Dora indicators that have not yet been determined are part of the prediction.

Under this interpretation, the output is not the number of dora currently known to be in the player's hand, and it is not multiplied by the probability that the player eventually wins.

The protocol only requires `players` to follow the “Seats” section, discrete values to be nonnegative integers, and `expectedValue` to be at least `0`. The engine need not use the recommended statistical interpretation. It may use this output for a dora-count prediction with another meaning, and the host still parses the same data structure.

## `opponent-score`

```json
{
  "players": [
    {
      "seat": 1,
      "prediction": {
        "distribution": [
          {"value": 1000, "probability": 0.10},
          {"value": 2000, "probability": 0.25},
          {"value": 3900, "probability": 0.45},
          {"value": 8000, "probability": 0.20}
        ],
        "expectedValue": 3955
      }
    }
  ]
}
```

The recommended statistical interpretation is the score produced by the corresponding player's hand at settlement, conditional on that player eventually winning the current hand. Ron and tsumo are not distinguished. The value excludes honba payments, riichi sticks, deposits, and other table awards.

The discrete distribution uses actual score values, while `expectedValue` may fall between them. The output is not multiplied by the probability that the player eventually wins.

The protocol only requires `players` to follow the “Seats” section, discrete values to be nonnegative integer points, and `expectedValue` to be at least `0`. The engine need not use the recommended statistical interpretation. It may use this output for a score prediction with another meaning, and the host still parses the same data structure.

## `action-recommendation`

### Request parameters

```json
{
  "candidates": [
    {
      "candidateId": "candidate:0",
      "action": {}
    }
  ]
}
```

| Field | Required | Format and Meaning |
| --- | --- | --- |
| `candidates` | Yes | the non-empty array of valid action candidates for which the host has completed rule verification. |
| `candidates[].candidateId` | Yes | the only opaque correlation ID in this request. |
| `candidates[].action` | Yes | a standardized action object. |

### Evaluation metric declarations

Action recommendations can declare any number of evaluation metrics. The metrics list the capability upper limit by `engine.hello` and determine the fixed set and order used by the current configuration based on the initialization results.

```json
{
  "id": "expected-placement",
  "title": {
    "default": "Expected placement",
    "zh-CN": "期望顺位"
  },
  "description": {
    "default": "Expected final placement after choosing this action."
  },
  "format": "number",
  "fractionDigits": 2,
  "preferredDirection": "lower"
}
```

| Field | Required | Format and Meaning |
| --- | --- | --- |
| `id` | Yes | the stable metric ID defined by the engine. Use lowercase ASCII letters, numbers, and hyphens, with a length of `1..64`. |
| `title` | Yes | a multilingual short title. |
| `description` | No | Multilingual description. |
| `format` | Yes | `number`, `percentage`, or `points`; used by the host to format values. |
| `fractionDigits` | No | The integer of `0..12`, specifying the number of decimal places to retain when displayed. `percentage` applies this precision after converting to a percentage. |
| `preferredDirection` | Yes | `higher`, `lower`, or `none`, indicating the preferred direction of the value. |

`format` only specifies the display format and does not define the statistical meaning of the metric. The meaning of the metric is given jointly by the stable ID, title, and description. Within the same major version of the engine, the format, direction, and meaning of the same metric ID must not be changed. `fractionDigits` only affects the display and does not change the values returned by the engine. If not provided, the host uses the standard numeric format and must not guess the number of decimal places based on the metric ID.

The initialization result can provide `primaryMetricId`, whose value must be an ID in the current `metrics`. The host can sort and evaluate details using the main indicators. When there are no main indicators, the host must not guess the indicators used for sorting based on the indicator ID.

The initialization result can provide `recommendationMetricId`, whose value must point to an indicator in the current `metrics` where `format` is `percentage` and `preferredDirection` is `higher`. The `[0, 1]` value of this indicator directly represents the relative recommended strength of each legal action, and the host can use this to draw recommendation bars. The engine is responsible for converting Q values, expected scores, or other internal evaluations into recommended strength; the host must not guess recommended strength based on the indicator ID, nor normalize undeclared indicators into recommendation bars on its own. When `recommendationMetricId` is absent, the host only highlights `bestCandidateId`, without drawing recommendation bars based on evaluation indicators.

`bestCandidateId` is always the recommended action ultimately chosen by the engine. `primaryMetricId` and `recommendationMetricId` only control the display of evaluation details and recommendation strength and must not be used to override this choice.

### Result

```json
{
  "bestCandidateId": "candidate:0",
  "candidates": [
    {
      "candidateId": "candidate:0",
      "metrics": {
        "q-value": 0.284,
        "policy": 0.423,
        "expected-placement": 2.18
      }
    },
    {
      "candidateId": "candidate:1",
      "metrics": {
        "q-value": 0.251,
        "policy": null,
        "expected-placement": 2.24
      }
    }
  ]
}
```

`bestCandidateId` must be one of the request candidates. Even if the engine does not provide any evaluation metrics, `bestCandidateId` must be provided.

When the currently configured `metrics` is empty, the result must not provide `candidates`. When `metrics` is not empty, the result must provide `candidates` and exactly cover all candidates in the request. Each candidate's `metrics` must exactly contain all indicator IDs declared during initialization; the values must be finite numbers that conform to the indicator format, and if there are no indicator values for the candidate at the moment, `null` is used. A single value of `null` does not change the indicator columns and interface layout already determined by the host.

The non-null values of `percentage` must be located in `[0, 1]`. The protocol does not require the sum of `percentage` values for different candidates to equal `1`, nor does it validate `bestCandidateId` based on `preferredDirection`. Recommended actions are directly determined by the engine.

## Sessions, status, and shutdown

The engine uses the following states:

| Status | Meaning |
| --- | --- |
| `starting` | The process has started but the handshake is not yet complete. |
| `uninitialized` | Handshake complete, not yet initialized. |
| `loading` | Loading or replacing configuration. |
| `ready` | Can accept analysis requests. |
| `busy` | Analysis in progress; new analysis requests should not be accepted when concurrency is not supported. |
| `error` | The current configuration is unavailable. Reinitialization can restore it. |
| `stopping` | Shutting down. |

When the state changes, the engine sends `engine.status` notification:

```json
{
  "jsonrpc": "2.0",
  "method": "engine.status",
  "params": {
    "state": "loading",
    "message": "Loading model weights",
    "error": null
  }
}
```

`state` is required; `message` and `error` are optional. `message` is for display only and must not carry data that the host is required to parse.

`engine.getStatus` is used for synchronization recovery and diagnostics, with a successful result being:

```json
{
  "state": "ready",
  "activeTasks": 0,
  "queuedTasks": 0,
  "lastError": null
}
```

`activeTasks` and `queuedTasks` are non-negative integers. The host must not rely on high-frequency polling; normal changes are pushed via notifications.

`task.status` can be sent when the engine starts or ends an analysis request:

```json
{
  "jsonrpc": "2.0",
  "method": "task.status",
  "params": {
    "requestId": "host-41",
    "state": "running",
    "outputs": [
      {"id": "action-recommendation", "version": 1}
    ]
  }
}
```

The allowed values for task status are `queued`, `running`, `completed`, `canceled`, `error`. Notifications do not replace the original request's JSON-RPC response.

`session.reset` and `session.close` both receive:

```json
{
  "sessionId": "game-17:seat-0:standard"
}
```

Both successful results are `{"ok": true}`. `session.reset` clears the incremental state of the specified session but allows the same ID to be used afterwards; `session.close` releases the session. Unknown sessions are also considered successful and must not affect other sessions.

Engines that support cancellation receive `request.cancel` notifications:

```json
{
  "jsonrpc": "2.0",
  "method": "request.cancel",
  "params": {
    "requestId": "host-41"
  }
}
```

Requests in the queue should be canceled immediately; running requests can be canceled at a safe point. After successful cancellation, the original request returns the `REQUEST_CANCELED` error. When cancellation is not supported or cannot be interrupted in time, the engine may complete the original request, and the host is responsible for discarding the outdated results.

`engine.shutdown` receives an empty object `{}`, first returns `{"ok": true}`, then sends `stopping` status and exits normally. The host can directly terminate the process in case of timeout, communication failure, or unresponsive process.

## Errors

Protocol error using JSON-RPC error response:

```json
{
  "jsonrpc": "2.0",
  "id": "host-41",
  "error": {
    "code": -32000,
    "message": "The requested output is not enabled.",
    "data": {
      "errorCode": "UNSUPPORTED_OUTPUT",
      "recoverable": false
    }
  }
}
```

`message` is short plain text. `data.errorCode` is a stable ASCII string that the host can determine; `data.recoverable` indicates whether it is possible to recover through new requests without restarting the process. Additional diagnostic data can only be placed in `data`.

Use the JSON-RPC standard numeric error codes `-32700`, `-32600`, `-32601`, `-32602`, and `-32603` to indicate parse errors, invalid requests, unknown methods, invalid parameters, and internal errors. Engine business errors use `-32000` and the following `errorCode`:

| `errorCode` | Meaning |
| --- | --- |
| `PROTOCOL_MISMATCH` | Protocol name or major version is not compatible. |
| `ENGINE_NOT_INITIALIZED` | Not yet successfully initialized. |
| `INITIALIZATION_FAILED` | Initialization failed to complete. |
| `INVALID_WEIGHT` | Weight missing, format error, or content incompatible. |
| `UNSUPPORTED_OUTPUT` | Output unknown, not enabled, or the current input mode is not supported. |
| `INVALID_HISTORY` | Game event missing, order incorrect, or content illegal. |
| `INVALID_CANDIDATES` | The action candidate is empty, duplicate, or invalid. |
| `INVALID_MODEL_OUTPUT` | The model produces missing, non-finite, or data that does not comply with the output contract. |
| `REQUEST_CANCELED` | The request has been cancelled. |
| `ENGINE_BUSY` | The current operating capability does not allow accepting new tasks. |

If any output in the analysis request fails, the entire request returns an error, and partial business results must not be included in the error response.

## Security boundary

Protocol compatibility does not mean the engine is trustworthy. The host must treat the engine program, manifest, text, paths, and all process outputs as untrusted input, limit message size and wait time, verify package paths, and must not execute manifest content through the Shell. The host should run the engine in a separate process and be able to terminate it in case of communication corruption, timeout, or abnormal exit.

## Host-generated result source identifiers

The protocol does not require the engine to generate or return source fingerprints. When results need to be cached, compared, or shown with their source, the host generates a stable identifier from what it actually launched and supplied. The identifier must cover every input that may change the result, including at least:

- Will affect the digest of the engine package file or executable file for execution;
- Summary of all currently used weight files;
- Actual device types, effective parameters, and operating configurations that may affect numerical accuracy;
- Output the contract ID and version;
- Initialize the representation of the determined results, metric ID, metric format, and preferred direction;
- A host post-processing version that will change the resulting values.

The host generates a source identifier for each output separately. When the same engine configuration provides multiple outputs, the shared program, weights, and parameter parts can be reused. Local file paths, multilingual titles, and descriptions must not be included in the stable identifier. Temporary states such as the number of process restarts and request sequence numbers are managed using separate run generations and do not belong to the stable source identifier. The protocol does not specify the field names, storage locations, or hash algorithms for internal host identifiers.
